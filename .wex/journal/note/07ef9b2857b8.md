# Préférence : prévenir avant de toucher au code partagé (lib prompt/screen)

Written: 2026-08-27
Author: agent:main

Complète les notes existantes sur la concision (`f3d1fcf60200`) et le rythme de travail (`e2fdc4482717`) : ici la consigne porte spécifiquement sur les modifications touchant du **code partagé/lib** (pas seulement du code applicatif).

Contexte : en discutant d'une amélioration du screen de progression (mode « push » plutôt que polling), l'agent propose de modifier `ScreenPromptResponse` dans la lib `prompt`. L'opérateur répond :

> "ca me dérance pas d'amélorer prompt, si il faut tout péter dans screen pour améliorer ça préviens moi avant"

Règle à retenir : il est acceptable de refactorer une lib partagée (pas seulement le code applicatif) si nécessaire, **mais l'agent doit prévenir avant** toute modification de grande ampleur ("tout péter"), pas seulement demander confirmation pour des petits patchs locaux.

Autre point du même échange : après un rollback trop empressé sur les fichiers filestate, l'opérateur a recadré :

> "Je sais que tu veux me faire plaisr mais calmos, ça a bougé"

→ Ne pas enchaîner les rollbacks/changements pour "faire plaisir" ou aller vite ; vérifier avec l'opérateur avant d'agir sur du code qui vient de bouger, surtout en présence de modifications concurrentes d'un autre agent (cf. note `7c3ad098b6d2`).
