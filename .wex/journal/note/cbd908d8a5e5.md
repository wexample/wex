# app::image/build --rebuild : pourquoi no-cache systématique et fusion avec --clear-cache

Written: 2026-08-27
Author: agent:main

Sur `app::image/build`, l'option `--clear-cache` a été supprimée (dead code, condition retirée) : le build est désormais toujours en `--no-cache`.

Raison : lors d'un renommage de package Python installé en editable (`pip install -e`) dans une image Docker, le script généré dans `/usr/local/bin` (ex. `pdf-serve`, un console_script) est produit *au moment du build*. Si Docker sert ce layer depuis le cache, le script reste généré depuis l'ancien nom de module même après un rebuild classique — Docker ne détecte aucun changement car le `pyproject.toml` renommé n'invalide pas forcément le layer concerné. Résultat observé : `ModuleNotFoundError: No module named 'pdf_generator'` qui persiste malgré plusieurs rebuilds successifs, jusqu'à forcer `--no-cache` explicitement.

Suite à ça, `--clear_cache` (dans `app/start`) et la nouvelle option `--rebuild` (ajoutée à `app/start` et `app/restart`) ont été fusionnées en une seule option `--rebuild` : elle déclenche à la fois `app::image/build --all` (sans cache) puis `docker compose up --build`. Décision explicite de l'opérateur : « je veux bien qu'il n'y en ait qu'un seul, l'idée c'est que ça bourine pour tout clear quoi » — préférence pour une option unique agressive plutôt que deux options fines à choisir correctement selon le cas.
