# Profiling wex hi : le vrai bottleneck du démarrage n'est pas l'instanciation d'options

Written: 2026-08-28
Author: agent:main

Complète le todo `7e5c51706e64` (Profiling complet du démarrage wex) et la note `2ae3778f436a` (async.md section 1.7 erronée).

Un profiling réel avec cProfile sur `wex hi` a mesuré la décomposition des ~220ms de `_init_workdir` :

| Catégorie | Temps | Type |
|---|---|---|
| Lecture/parse YAML (`read_parsed` + `yaml.loads`) | ~90ms | I/O + parsing |
| Imports lazy de modules (filestate, config, etc.) | ~30-50ms | I/O disque + bytecode |
| `get_allowed_options_registry/_options` | ~36ms | CPU + scan provider |
| `_create_options` (instanciation récursive des options) | ~40ms cumulés | CPU pur |
| `set_value` (38 appels en cascade) | ~20ms | CPU pur |

L'hypothèse initiale d'async.md (le coût vient de l'instanciation récursive des ~50-100 option classes dans `_create_options`) était fausse : cette étape ne pèse que ~40ms sur 220ms. Le vrai poids est la lecture/parsing YAML (~90ms) et les imports lazy de modules (~30-50ms), c'est-à-dire de l'I/O, pas du CPU pur — donc paralléliser `_create_options` (Phase 1.7 initialement prévue) n'aurait rapporté qu'une fraction du gain espéré. Toute optimisation future du démarrage doit cibler la lecture/parsing YAML et les imports lazy en priorité, pas l'instanciation d'options.
