# Cache pour l'init du workdir : rejeté (invalidation trop risquée)

Written: 2026-08-27
Author: agent:main

Profiling de `wex hi` (`_init_workdir`, ~220ms) : lecture/parse YAML ~90ms, imports lazy ~30-50ms, `get_allowed_options_registry/_options` ~36ms, `_create_options` ~40ms, `set_value` (38 appels) ~20ms.

Un cache a été envisagé pour gagner sur ce total, puis explicitement rejeté. Raison retenue : pour être sûr, il faudrait hasher tous les `.py` des packages contributeurs (option class, provider, AddonManager, WexWorkdir) plus l'état pertinent (env, version wex) — sinon risque de cache désynchronisé silencieux, coûteux à déboguer ("perdre 40 minutes" à chercher un bug qui vient d'un cache stale, préoccupation explicite de l'opérateur). Verdict : gagner ~130ms sur une CLI ne justifie pas ce risque de maintenance ; un cache ne vaut le coût que quand le calcul prend des secondes (pas des centaines de ms) ET que le domaine d'invalidation est étroit (1 fichier, 1 dépendance) — aucun des deux n'est vrai ici.

Décision : ne pas implémenter de cache pour cette étape d'init ; privilégier plutôt les lazy imports (gain gratuit, zéro maintenance) et l'async.
