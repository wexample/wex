# AppsRegistry : lock retiré ou mixin — décision finale vers le mixin

Written: 2026-08-27
Author: agent:main

Contexte : lors du refactor du registre d'apps vers `AppsRegistry(SharedRegistry, DiskPersistedRegistry)`, se posait la question du lock cross-process (`fcntl.flock`) que `apps_registry.py` a et que `DiskPersistedRegistry` n'a pas.

Deux options discutées :
- Retirer le lock : la fenêtre de race est jugée minuscule, le pire cas (entrée manquante) est facilement réparable via `purge_stopped` ou `host/update`, aucun incident terrain connu.
- Extraire le pattern dans un `WithFileLockMixin` composable (`class MyReg(WithFileLockMixin, DiskPersistedRegistry[T])`), opt-in, sans polluer le framework de base.

L'IA a d'abord validé la suppression (YAGNI), mais l'opérateur ne se souvenait plus de la raison d'origine du lock ("je me souviens vaguement d'avoir mis ce lock, je sais plus vraiment par peur de quoi") — donc cette rationale d'origine est perdue, pas de piste à creuser côté historique.

Décision finale, motivée par une préférence de design générale de l'opérateur (pas seulement ce cas précis) : "Je suis pas contre que les trucs soit robustes dès le départ, que ce soit légèrement sur-engeneeré by design pour que le jour ou on s'en sert ailleurs on aies meme pas a y penser et que tout marche comme attendu." → on garde le pattern lock, mais sous forme de mixin composable plutôt que de le laisser en spécifique à AppsRegistry.

À vérifier dans le code actuel : si `WithFileLockMixin` existe, cette note explique pourquoi il a été préféré à un simple retrait du lock. Si le refactor a divergé plus tard (indices dans la suite de la session : approche jugée "trop lourde"), le lock pourrait avoir été simplifié à nouveau — vérifier l'état réel du code.
