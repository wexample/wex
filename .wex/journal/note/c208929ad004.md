# Registrification : décisions de design Protocol/hiérarchie (complète 6269e495765f, e3a174b669f8)

Written: 2026-08-28
Author: agent:main

Décisions prises pendant la conception de la registrification, avant implémentation — complètent les todos `6269e495765f` (Protocol Registrable + hiérarchie Registry) et `e3a174b669f8` (KernelRegistry → DiskPersistedRegistry).

**Protocol vs Mixin** : Protocol `Registrable` par défaut. Garde-fou explicite de l'opérateur : « si ça couvre notre cas à 100%, ok, si on est trop serrés dedans -> mixin ». Bascule vers mixin seulement si le Protocol s'avère trop contraignant en pratique.

**Hiérarchie de Registry retenue, en 3 variantes** :
- `Registry[T]` (base) : stocke un dict<key, T> (instances ou classes), pas d'init managée, juste du lookup — ex. dictionnaires statiques d'OptionClasses.
- `SingletonRegistry[T]` (hérite de `Registry`) : stocke des **classes**, instance maintenue par le Registry, init managée via `init_all_sync/async()` avec dépendances topologiques — ex. AddonManager, Middleware, ScriptRunner, StepGuard.
- `DiskPersistedRegistry[T]` : idée de l'opérateur — englobe le cas `KernelRegistry`, paramétrée par un `StructuredFile` (YamlFile, JsonFile...) passé en argument. Couvre KernelRegistry (JSON) et les futurs cas (caches YAML, état persistant d'addons, etc.) avec une seule abstraction, jugée « plus propre que mon plan initial » par l'agent.

**Rétro-compatibilité** : explicitement écartée pour ce chantier — « La rétro compta je m'en fous, je préfère qu'on corrige tout tout de suite. »

**`[T]` générique vs `@base_class`** : le `[T]` n'est que du typing générique Python (comme `list[int]`) pour les vérifications statiques de type — `Registry` elle-même reste décorée `@base_class` comme le reste du code. Les deux mécanismes sont orthogonaux, ne pas les confondre.
