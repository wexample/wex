# Chemins de lecture de la documentation (cas A/B/C) et stubs obligatoires

Written: 2026-08-27
Author: agent:main

Trois façons de lire le knowledge d'un projet, identifiées lors d'une revue de roadmap :

- **Cas A — Le `README.md` généré** : déclenché par `state/rectify` via `AppReadmeConfigValue`, seul agrégateur fonctionnel à ce jour.
- **Cas B — `AGENTS.md` / `CLAUDE.md`** : lu par un agent qui ne connaît pas wex. Aujourd'hui une chaîne Python en dur (`with_ai_workdir_mixin.py:15`) qui dit « parcours `.wex/knowledge/` » sans savoir ce que contient réellement le dossier.
- **Cas C — L'humain qui ouvre le fichier** : fonctionne déjà, seule contrainte : les fragments doivent rester lisibles isolément.

Mécanisme des pages obligatoires : `ManagedWorkdir.get_required_knowledge_pages()` retourne `{"<dossier>/<nom>": contenu_initial}`, injecté par `_build_knowledge_children()` dans les dossiers `usage/` et `contributing/` déjà déclarés (une sous-classe étend via `{**super()..., ...}`). Niveaux : `ManagedWorkdir` → `usage/overview` + `contributing/architecture` ; `PythonPackageWorkdir` → ajoute `usage/quickstart` ; `PythonWorkdir` → rien.

Ces pages ne sont que des **stubs** : `rectify` crée par ex. `usage/overview.md.j2` avec un commentaire Jinja énonçant la consigne, mais rien n'est rédigé — le README continue d'afficher la `description` de `config.yml` en attendant. Le remplissage réel du contenu est une étape séparée, confiée à un agent `author` muni du contrat correspondant. Un mécanisme distinct permet à filestate d'utiliser un agent pour rédiger le contenu d'un fichier — traité ailleurs, hors de cette conversation.
