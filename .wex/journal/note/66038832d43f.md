# Option --async générique sur les commandes : abandonnée, pourquoi

Written: 2026-08-27
Author: agent:main

Idée explorée puis abandonnée : ajouter un attribut `@async` sur les commandes wex, avec une option core `--async`/`--sync` (au même titre que `-vvv`), pour lancer une commande en arrière-plan.

Règle de simplification envisagée : une commande lancée en `--async` ne retournerait rien d'exploitable (`None`, à l'image de `wexample_app/response/null_response.py`), ce qui évite tout le mécanisme de job id / store de résultats / `wex job/wait`.

Le cas d'école pour juger la faisabilité était `core::webhook/listen`, qui a déjà une option ad-hoc `--asynchronous` (voir `wex-core/src/wexample_wex_core/addons/core/commands/webhook/listen.py:27`). Cette commande fait deux choses :
1. Spawn du subprocess — généralisable trivialement (`subprocess.Popen([sys.executable, sys.argv[0], <command>, ...args_sans_async])`).
2. Attente active que le port soit bindé (polling 10×0.5s) puis log "started on port X (pid Y)" ou erreur "spawned but port not bound" — logique métier spécifique au fait que cette commande démarre un daemon réseau, non généralisable à un mécanisme `--async` générique.

L'opérateur voulait un `--async` générique 100% iso-fonctionnel à ce cas existant, condition non remplie à cause du point 2. Résultat : abandon de l'approche "attribut async sur les commandes", réorientation vers l'usage d'`async`/`await` en interne du code Python core pour des gains de performance (roadmap couverte par un autre sujet).
