# Règles Python : portée et hook de formattage

Written: 2026-08-27
Author: agent:main

Scope confirmé et implémenté : les règles de style Python ne se déclenchent que pour un `.py` sous le `src/` d'un package Python (workdir Python). Un `.py` de test, de script, dans un `.venv` ou dans un dépôt non-Python ne déclenche rien — le périmètre volontairement le plus étroit possible, extensible plus tard si besoin.

Implémentation (vérifiée en conditions réelles, `PreToolUse:Edit` renvoie bien les règles en `additionalContext` sans jamais bloquer l'édition) :
- `PythonCodeFormatter` dans `wex-addon-dev-python`, enregistré via `FormatterContributingAddonMixin` (point d'extension déjà existant pour les addons).
- `matches_path()` ajouté sur `AbstractFormatter` et `resolve_formatter_for_path()` ajouté, car jusqu'ici un formatter ne se résolvait que par son nom depuis un contrat.
- Hook `PreToolUse` sur `Edit|Write|MultiEdit` dans `claude_agent.py`.

Première règle posée (en tête du fichier de règles) : un fichier par classe, une classe par fichier ; classes, fonctions (helpers), constantes et enums séparées dans des répertoires dédiés. Deux précisions ajoutées à la règle plutôt qu'inventées : la correspondance nom de fichier ↔ nom de classe est déjà vérifiée automatiquement au rectify par `ClassNameMatchesFileNameOption` (ce qui en fait une erreur, pas une préférence) ; rien n'interdit aujourd'hui une seconde classe dans le même fichier, d'où le besoin de l'expliciter. Répertoires réellement utilisés dans le repo au moment de l'audit : `const/` (14 packages), `helper/` (10), `enums/` (3) vs `enum/` (2, à unifier), `classes/` (3).
