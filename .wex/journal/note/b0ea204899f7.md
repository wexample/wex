# Screen d'avancement (rectify async) abandonné pour les logs

Written: 2026-08-27
Author: agent:main

Pendant le travail sur l'affichage de progression du rectify async (`wex app::state/rectify --dry-run`, 32 workers), une version "screen" (redraw en place, façon Docker) a été tentée puis **abandonnée au profit d'un simple log par item** (`[N/488] /path`, ordre interleavé assumé, spam accepté).

Raison : deux bugs jamais élucidés malgré plusieurs itérations (~2h) :
- Clignotement persistant malgré un mécanisme anti-flicker (voir plus bas).
- Empilement de lignes "Inspecting N/488" qui se répètent à des positions différentes à chaque run, sans message d'erreur — cause non identifiée (print fantôme depuis un worker ? interaction terminal/IDE/ANSI ? jamais tranché).

Une piste (wrap de lignes trop longues faussant le compte de clear du screen) a été corrigée (troncature des paths à 100 chars, `get_display_path()`) mais n'a pas réglé le problème de fond.

Décision de l'opérateur : "Yes rollback en log." — le screen est jugé trop fragile pour ce cas d'usage (workers concurrents + ANSI), la version log est jugée plus fiable même si moins jolie.

**Ce qui reste dans le code malgré le rollback** : le patch apporté à la lib `prompt` sur `ScreenPromptResponse` — un mode "push" en plus du poll classique :
- `threading.Event _tick_event` + méthode publique `request_refresh()` (un thread peut réveiller le redraw immédiatement au lieu d'attendre le prochain poll).
- `min_refresh_interval` : gap minimum entre deux redraws consécutifs (anti-flicker, façon cap FPS) — les pushs pendant le gap sont mémorisés et consommés au gap suivant.

Ce patch est additif et non-breaking (rien ne casse pour les callers existants) mais **n'est actuellement utilisé nulle part** dans le code puisque le screen a été abandonné pour ce cas d'usage. Il reste disponible si un futur besoin d'affichage temps-réel multi-thread se présente — mais garder en tête que même avec ce mécanisme, le clignotement et l'empilement n'ont pas été résolus ici.
