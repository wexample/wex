# Rectify parallèle abandonné : black sature le CPU avec 32 workers

Written: 2026-08-27
Author: agent:main

Tentative de paralléliser `wex app::state/rectify --dry-run` (build_operations flatten + pool unique, 32 workers) sur un cas réel de 488 items.

Symptôme observé : la progression ralentit drastiquement puis semble se figer (168 → 192 items en plusieurs secondes, puis 30s sans aucun mouvement), donnant l'impression d'un freeze alors que ça avance encore, très lentement.

Cause racine diagnostiquée : chaque fichier `.py` déclenche `FormatOption._apply_content_change` qui appelle `black`. Black est mono-thread par exécution. Avec 32 workers Python lancés en parallèle sur une machine à ~8 cœurs réels, on obtient 32 appels black simultanés qui saturent le CPU et provoquent du context-switching massif — le gain de parallélisme attendu est annulé, et l'expérience utilisateur devient pire qu'en séquentiel (impression de blocage total).

Décision : rollback complet de la parallélisation pour rectify — `abstract_item_target.py` et `item_target_directory.py` reviennent à la version séquentielle récursive (HEAD). Seul le vrai fix indépendant est conservé : import top-level de `black` dans `format_option.py` (au lieu d'un import lazy problématique).

À retenir pour toute reprise future de la parallélisation de rectify (cf. todo `588120d55bf4`) : le goulot n'est pas l'I/O ou le walk, c'est le CPU-bound de black lui-même — un pool de workers ne doit pas dépasser le nombre de cœurs réels pour ce type de charge, sous peine d'être contre-productif.
