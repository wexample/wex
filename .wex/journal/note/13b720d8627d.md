# Mécanisme path() pour maintenabilité de la knowledge

Written: 2026-08-27
Author: agent:main

Décision de conception pour les fichiers `.wex/knowledge/*.md.j2` : au lieu de laisser la doc pourrir en silence quand un chemin de code cité (ex: `cli/install`) disparaît ou change, on introduit une fonction utilisable dans les templates j2 qui vérifie l'existence du chemin et **plante au `rectify`** s'il n'existe pas.

Implémenté sous le nom `file_path()`, appliqué comme cobaye sur `usage/installation.md` (converti en `.md.j2`) : installation globale, mode dev, désinstallation — chaque chemin de code cité passe par `file_path()`. `{{ package_name }}` fonctionne aussi dans les fichiers knowledge (même contexte que les autres templates).

Règle de conversion : `knowledge()` essaie `.md.j2` puis `.md` (comme `_render_section()` déjà) — on ne convertit en `.j2` que les fichiers qui référencent effectivement du code ; le reste reste du markdown lisible à l'œil.

**Renommage décidé en fin d'échange** : `file_path()` → `path()`. Raisons données par l'agent : « file » est faux dès qu'on pointe un dossier (`bin/`, `tests/unit/`), et la vérification est le seul comportement de la fonction donc pas besoin de la nommer — il n'y aura jamais de version non vérifiée. Alternative envisagée si on veut un contrat explicite à la lecture : `existing_path()`. `file_ensure` écarté car « ensure » laisse croire que ça crée le fichier. L'opérateur a validé : « Ok pour path ».
