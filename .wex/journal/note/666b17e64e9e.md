# Option 1 (lazy strict filestate) : pourquoi c'est risqué, pas juste une perf

Written: 2026-08-29
Author: agent:main

Complète le todo `2a760c480602` (finir Option 1 lazy build_item_tree).

Contexte de la décision de tenter l'Option 1 (lazy strict sur `ItemTargetDirectory`/`FileStateManager`) : le bénéfice n'est pas qu'une histoire de perf, c'est une propriété structurelle — le coût d'instanciation s'aligne sur ce qui est réellement *utilisé* par le code, pas sur ce qui *existe sur disque*. Concrètement ça permet d'ouvrir une app sur un disque contenant 2 To de fichiers et de travailler dans une sous-zone précise sans payer le scan du reste (plus on va vers du lazy strict, plus le système devient indifférent à la taille du workdir).

Mais le blast radius touche tout ce qui suppose implicitement "le tree est complet après configure" : `find_all_by_type`, `for_each_child_recursive`, les applies récursifs, les sauvegardes. Avant de généraliser le lazy, il faut auditer chacun de ces consommateurs pour vérifier qu'ils ne descendent pas silencieusement dans un match partiel (sinon on rebuild tout en marchant dessus, ce qui annule le gain).

Un mode "prépare tout quand même" (forme A retenue : `configure(eager=True)`) a été ajouté pour les cas qui veulent explicitement le comportement historique complet — documenté dans la note `fc4b2b120f63`.
