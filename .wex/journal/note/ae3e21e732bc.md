# Hooks SDK Claude pour injecter les règles Python à l'édition

Written: 2026-08-27
Author: agent:main

Décision d'architecture pour appliquer systématiquement les règles de codage Python aux agents "main" qui éditent du code, sans dépendre du choix de l'agent ni de configs globales Claude Code.

**Piste rejetée** : les fichiers `settings.json` de Claude Code (`~/.claude/`, `<projet>/.claude/`) ne s'appliquent pas ici — le projet utilise des agents spécialisés via le SDK directement, avec `setting_sources=[]` (voir `claude_agent.py:528`) qui désactive explicitement la lecture de ces settings.

**Piste retenue** : le SDK (`claude-agent-sdk` 0.2.87) accepte un champ `hooks` dans `ClaudeAgentOptions` — un dict d'événements (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`…) vers des `HookMatcher`, dont les callbacks sont des **fonctions Python** (pas des commandes shell). `ClaudeAgent` construit déjà ses options lui-même dans `claude_agent.py:515`, il suffit d'y ajouter `hooks`.

Point bloquant initial : un `PreToolUse` classique ne peut que bloquer l'appel d'outil (`permissionDecision`), ce qui forcerait l'agent à réessayer — jugé inutilisable ("Si on peut que bloquer le tool ca sers a rien"). Vérification faite : `PreToolUseHookSpecificOutput` expose aussi `additionalContext`, ce qui permet de laisser passer l'`Edit`/`Write` **et** d'injecter les règles dans le contexte, sans blocage ni retry (il existe même `updatedInput` pour corriger le contenu écrit au vol, non retenu ici).

**Plan retenu** :
- Les règles vivent dans un `PythonCodeFormatter` dans `wex-addon-dev-python`, calqué sur `AppDocFormatter` (même classe de base, même `get_writing_rules()`). Une seule source de règles pour deux consommateurs : le nouveau hook d'édition, et les trois points d'appel existants qui savent déjà s'en servir (`agent/query`, `contract/write`, `ai_generated_config_value`).
- Un hook `PreToolUse` dans `wex-addon-ai` envoie ces règles en `additionalContext` quand un agent édite un `.py`.
- Aucune activation/désactivation manuelle : le déclenchement se fait sur l'extension du fichier édité, donc les règles ne s'appliquent jamais ailleurs — répond à l'inquiétude "j'ai peur qu'il aies ces règles dans un cas ou elle ne doivent pas s'appliquer".
- Portée précisée en fin d'échange : les règles s'activent pour les fichiers `.py` du `src` des packages workdir uniquement (confirmé juste après ce subject).
