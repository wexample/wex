# Système d'exploration pour agents : famille de commandes `search`

## Intention

wex est un IDE pour agents : des outils et des conventions qui leur permettent de
développer en autonomie. Dans un IDE humain la recherche est centrale — c'est ce qui
permet de toujours s'y retrouver. Il nous manque l'équivalent.

Ce qui fait la valeur n'est pas le matching : un agent a déjà `Grep`. Ce qu'il n'a pas,
c'est de savoir **où** chercher — quelles apps composent la suite, quel dossier est `src`
dans ce langage-là. Une commande qui ne répond pas à ça est un ripgrep en moins bien, et
ne sera pas utilisée.

Contraintes posées : app level **et** suite level ; textuel et opérationnel d'abord, pour
un usage au plus tôt ; prompté pour que les agents l'utilisent spontanément.

## Forme commune

Quatre commandes, une seule forme, pour qu'un agent qui en apprend une les ait toutes
apprises :

- `--query <texte>` — insensible à la casse, sous-chaîne, pas de regex
- `--scope self|suite|stack` (défaut `stack`)
- `--lines` — `chemin:ligne: texte` au lieu d'une ligne par unité
- réponse toujours en `fichier:ligne` + extrait, chemins relatifs à la racine du scope
- tags `EffectTag.READ_ONLY` + `AudienceTag.AGENT_SAFE`

## Phase 0 — extraire la résolution de périmètre

`collect_search_paths()` dans
`PACKAGES/PYTHON/wex/wex-addon-app/src/wexample_wex_addon_app/helper/knowledge_search.py`
résout déjà `self` / `suite` / `stack` pour le knowledge. La généraliser en un helper
partagé (rendre le sous-chemin `.wex/knowledge` paramétrable, ou renvoyer les workdirs
plutôt que des chemins) et faire passer `knowledge/search` dessus sans changement de
comportement.

C'est cette brique qui rend « app level et suite level » gratuit pour les trois autres.

## Phase 1 — `app::journal/search`

Presque gratuit : notes, todos, subjects et done sont des `.md` dans
`.wex/journal/{note,todo,subject,done}/`, et `note/list`, `todo/list`, `subject/list`
existent déjà (`wex-addon-app/.../commands/{note,todo,subject}/list.py`).

- **une seule** commande avec `--kind note|todo|subject|done` (répétable), pas trois
- tri : plus récent d'abord
- sortie : `<kind> <id> <titre>` + la ligne qui matche
- motivation : pouvoir manager les tâches, retrouver une décision prise il y a deux
  semaines sans connaître son id

Aucune recherche textuelle n'existe aujourd'hui sur le journal.

## Phase 2 — `app::sources/search` (le vrai chantier)

### 2a. Le point d'accroche : `CodeBaseWorkdir`

`wex-addon-app/src/wexample_wex_addon_app/workdir/code_base_workdir.py` n'expose
aujourd'hui **aucune** méthode de sources. Y poser :

```python
def get_source_paths(self, include_tests: bool = False) -> list[Path]:
```

surchargée par `PythonWorkdir` (`wex-addon-dev-python`), `PhpWorkdir`
(`wex-addon-dev-php`), `JavascriptWorkdir` (`wex-addon-dev-javascript`). Les constantes
`PATH_DIR_SRC` / `PATH_DIR_TESTS` existent déjà dans
`packages/filestate-python/.../const/path.py`.

C'est cette méthode qui garde la commande ignorante du langage. `--tests` n'est alors que
le passage du booléen.

Question ouverte : est-ce le workdir ou le service qui répond ? Trancher au moment de
l'implémentation, le workdir semble le bon niveau (le service décrit un runtime, pas une
arborescence).

### 2b. La commande

- scan textuel simple, pas d'index
- filtres : `--tests`, `--ext py,php`, `--max`
- retourner des `fichier:ligne` exploitables — c'est ce qui ne ferme pas la porte à la
  couche suivante

### 2c. Plus tard, pas maintenant

Indexation et recherche structurelle (« toutes les instances de la classe `Truc` »,
définitions vs usages). À ne pas concevoir aujourd'hui, seulement à ne pas s'interdire.

## Phase 3 — `ai::session/list` puis `search`

Besoin : « je ne sais plus à quel agent j'ai demandé quoi ».

Les sessions vivent dans `.wex/ai/sessions/<agent>/<id>/` avec `meta.json` (`agent_name`,
`name`, `turn_count`, `last_message_at`, `subjects`) et `conversation.jsonl`. Classes :
`SessionWorkdir`, `SessionMetaJsonFile`, `SessionsRootWorkdir`, `SessionsSuiteWorkdir`
dans `wex-addon-ai`. **Aucune commande ne liste les sessions.**

- `list` d'abord : trié par `last_message_at`, colonnes agent / sujets / tours / date —
  ça répond déjà à la question la plupart du temps
- `search` ensuite : dans les `subjects` du meta, puis dans `conversation.jsonl`

## Phase 4 — prompter

**Un seul** paragraphe dans `wex-addon-ai/.../resources/ai/shared/context.j2`, qui nomme
la famille et le réflexe (chercher avant de conclure que ça n'existe pas). Pas quatre : le
détail appartient aux descriptions de commandes, que les agents lisent.

Le paragraphe knowledge actuel est à fondre dedans, pas à doubler.

## État

Fait, les quatre phases.

Deux écarts au plan, tranchés à l'implémentation :

- **Les sources sont résolues depuis le chemin, pas depuis le workdir.** Une recherche qui
  balaie la pile a quatre-vingts chemins d'apps et aucun workdir ; en instancier autant pour
  lire un nom de dossier n'a pas de sens. `helper/source_tree.py` répond depuis le chemin, et
  `RepoWorkdir.get_source_directories()` est la même réponse atteinte par l'objet — c'est là
  qu'on surcharge le jour où une arborescence sort du lot.
- **Le scope par défaut n'est pas le même partout.** `stack` pour le knowledge, le journal et
  les sessions ; `self` pour le code. La doc est un corpus balayable, le code non.

`ai::session/search` ne lit que les métadonnées par défaut — les sujets qu'une conversation
ouvre au fil de l'eau sont un index écrit du travail. `--messages` ouvre les transcripts.

Reste ouvert, non conçu : l'indexation et la recherche structurelle (« toutes les instances
de `Truc` »). Rien ne la ferme — un match est un fichier et une ligne.
