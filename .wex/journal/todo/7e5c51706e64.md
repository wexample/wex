# Profiling complet du démarrage wex (registre vs import direct)

Opened: 2026-08-27
Updated: 2026-08-27
Author: agent:main

Objectif : décider si l'async pour les imports d'addons (actuellement fait directement dans `wex.py:exec()`, cf. roadmap `async.md` phase 1.5) doit passer par le pattern `Registry` standard, ou rester une mécanique séparée ad-hoc.

Demande de l'opérateur : "a performance égale, je préfère une version uniforme qui passe par le registre. Tu peux aussi utiliser `wex hi` pour tester les perfs d'une commande complète qui ne fait pas grand chose. Tu peux me faire le profiling complet ?"

État au moment où la conversation s'arrête : un patch d'instrumentation temporaire a été ajouté dans `wex.py` pour mesurer le temps de chaque phase de démarrage (import des addons, `register_items()`, exécution de la commande). L'agent a dit vouloir "laisser tout en place pour l'instant, on retire après lecture des résultats" — le profiling n'a pas été exécuté/lu, et le patch temporaire n'a jamais été confirmé comme retiré.

À faire :
1. Vérifier si un patch d'instrumentation temporaire traîne encore dans `wex.py` (local/wex/src/common/wex.py) et le retirer si oui.
2. Lancer le profiling sur `wex hi` (commande légère, choisie exprès pour isoler le coût de démarrage du coût métier).
3. Comparer coût de l'approche "import parallèle direct dans wex.py" vs "résolution des classes déplacée dans le Registry" (ex. `register_addon_modules([...])` async).
4. Trancher selon le principe : à performance égale, préférer la version qui passe par le Registry (uniformité), même si l'implémentation directe dans wex.py était plus simple à écrire au départ.
