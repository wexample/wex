# app::setup/install : editable cassé si lancé au niveau package plutôt que suite

Opened: 2026-08-27
Updated: 2026-08-27
Author: agent:main

Bug non corrigé, contourné une seule fois manuellement.

Si on lance `wex app::setup/install --env local` depuis un package (ex. `wex-addon-master`) plutôt que depuis la racine de la suite parente (`.wex/config.yml` au niveau `PACKAGES/PYTHON`), le `app_workdir` injecté est le package lui-même. Conséquence : `_pre_install_python_packages_editable` ne se déclenche jamais, et pip résout les dépendances transitives (ex. wex-core → helpers → …) comme des wheels classiques, écrasant silencieusement les installs `-e` (editable) déjà en place pour les autres packages de la suite.

Symptôme observé : après install d'un nouvel addon, `wex package::suite/status` (ou toute autre commande) plante car `wexample_helpers`/`wexample_wex_core` sont réinstallés en copie figée au lieu de pointer vers les sources locales — les modifications de code ne sont plus vues. Un symptôme dérivé possible : `TypeError: _create_workdir_state_manager() got an unexpected keyword argument 'configure'`, qui n'est pas un bug de filestate mais juste la conséquence d'un wex-core resté en version copiée obsolète (signature différente entre le code local à jour et la copie installée).

Contournement qui marche : relancer `app::setup/install` depuis la racine de la suite (pas depuis le dossier du package) — ça redéclenche bien `_pre_install_python_packages_editable` sur tous les packages de la suite. Il faut aussi réinstaller en editable *chaque* package dont la version copiée est devenue incohérente (pas seulement celui qu'on visait) — dans le cas traité, il a fallu réinstaller à la fois `wexample-helpers` et `wex_core`.

À corriger dans la commande : soit détecter qu'on installe un package rattaché à une suite et forcer la résolution du workdir au niveau de la suite, soit avertir explicitement quand un install au niveau package risque d'écraser des installs editable de la suite parente.
