# Design-rules consultation: format & service-per-language open points

Opened: 2026-08-27
Updated: 2026-08-27
Author: agent:main

Contexte : les règles "design" (ex: un fichier par classe, séparation classes/helpers/constantes/enums) sont des règles d'architecture, pas de syntaxe — les fournir dans le hook Edit est trop tard puisqu'elles décident *quels fichiers existent*, pas comment une ligne s'écrit. Décision actée dans l'échange : garder deux familles séparées sur le formatter, `get_writing_rules()` (reste le filet à l'édition : `default=` vs `factory=`, appel `super().__attrs_post_init__()`, extension `.js` sur les imports relatifs...) et `get_design_rules()` (consultées en amont, à la conception). Idée retenue : créer des agents "développeur" génériques (toutes apps, pas de package spécifique), avec une ligne de prompt supplémentaire : "Avant de proposer des solutions d'architecture de code, tu dois consulter les règles de design ici [à définir]".

Deux questions restent tranchées à faire :
1. Point d'entrée langages : lister les langages en dur dans le prompt de l'agent, ou avoir un point d'entrée commun qui répond "les langages disponibles sont Python / PHP, etc." ?
2. Nature du stockage des règles de design : simple chemin vers un fichier `.md`, un tool, une capability, ou un nouveau concept type "skill" ?

Prolongement posé en fin d'échange, sans réponse dans la conversation : créer un service "python" (à l'image des services PHP/Symfony existants) et organiser les agents développeur par service — avec la question ouverte de comment charger (ou s'en passer) les instructions JS quand du code JS apparaît dans un programme Python.

Note pour qui reprend : au moment de cette conversation, `wex ai::design/rules` (avec `--formatter <name>`) n'existait pas encore — si cette commande existe déjà, ce sujet est probablement résolu et il faut vérifier si l'organisation par service (point 2 du prolongement) l'est aussi avant de retravailler dessus.
