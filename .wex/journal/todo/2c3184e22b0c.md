# Types de process contribués par un bundle monté (python + déclaration)

Opened: 2026-09-16
Updated: 2026-09-16
Author: agent:addon:ai/editor (app-board)

## But

Permettre à un bundle monté dans les conteneurs d'un board (ex.
`home-habilis/pdf-generator`, du python + une déclaration yml/json) de
contribuer des types de process que le worker wex sait exécuter — premier cas
réel : `hh:md-to-pdf` sur l'app `doc-qms` de HOME_HABILIS.

## Ce qui existe déjà (16/09/2026, branché et vérifié depuis app-board)

- `AbstractAddonManager.get_process_type_family_classes()` (wex-core) : hook par
  lequel un addon contribue ses familles ; `ProcessAddonManager` y répond
  `[FileStateProcessTypeFamily]`.
- `ProcessTypeRegistry.from_kernel(kernel)` (wex-addon-process) : le registre
  est construit depuis les addons chargés, plus aucune liste en dur. Les deux
  appelants : `commands/run/execute.py` et `service/process_run_service.py`.
- Le serveur d'agents sert `GET /data/process_type` (`wex-addon-ai/helper/data.py`,
  `_process_type_records`) : interroge les addons via le hook, uuid dérivé du nom
  (`uuid5`), le board projette ça en table (`board:process-type:sync`).
- Un type est une classe simple sans kernel (`AbstractProcessType` : `name`,
  `label`, `run(context)`) ; une famille déclare ses types sous un préfixe
  (`filestate:`, demain `hh:`).

## Contraintes posées par l'opérateur

- **Le wex du conteneur est le même que celui du host.** On ne référence donc
  jamais un type en dur dans wex : la liste est dérivée à chaud de ce qui est
  monté dans l'environnement où wex tourne. Au mieux un cache/registry
  reconstruit au démarrage — et différent sur le host et dans le conteneur.
- Le bundle apporte du python + une déclaration yml ou json, monté dans les
  conteneurs du board ; wex le charge comme une famille de plus, et c'est wex,
  seul, qui remonte la liste au board.
- Idée en cours (notée dans app-board, todo `2967a4664472`) : remplacer le
  `/data/<kind>` HTTP par des fichiers que wex écrit dans un dossier convenu
  (hors du `.wex/data/` d'une app — plutôt `/var/lib/wex/data/<kind>/`), le
  serveur HTTP étant destiné à disparaître une fois le chat passé sur la queue.

## À trancher ici (le cœur du ticket)

1. **Forme de la déclaration côté bundle** : quel fichier, où dans le bundle,
   et ce qu'il nomme (module python, classe de famille, préfixe).
2. **Découverte** : comment wex trouve les bundles montés depuis le workdir
   d'une app (le chemin type : `<app>/service/board/bundles/<vendor>/<nom>/`),
   sans balayage fragile.
3. **Chargement** : importer du python arrivé par un montage — sys.path, cycle
   de vie, et ce qu'on refuse (un type dont l'import échoue ne doit pas faire
   tomber le worker ; cf. le runner qui sait déjà mettre un run en `failed`).
4. **Cache/registry** : où il vit, quand il se reconstruit (démarrage du
   conteneur, installation), et son invalidation.
